# 网页目标模式设计计划：先规划落盘，再按节点执行

状态：设计与源码实现约定。本文不作为端到端集成验收通过的证明。实际操作入口见 [网页目标模式操作说明](HOST_GOAL_MODE.zh-CN.md)。

## 1. 产品目标与已确定的选择

长线任务的目标、计划、进度、问题和执行证据保存在本机，不依赖 ChatGPT 某一段聊天的上下文。新对话读取本地状态后能够继续同一个任务。

- 第一版入口为 ChatGPT 对话命令，不新增终端 CLI。
- 第一版由网页模型主动接手，采用串行节点，支持阻塞、暂停、返工和重新规划。
- ChatGPT 网页开启目标模式后，先讨论需求并通过工具生成本地计划；完整计划成功落盘后进入 awaiting_confirmation，用户阅读并在网页对话明确通知开始后才允许业务执行。
- 计划必须包含最终验收目标、验收方式、节点步骤和 state 管理规则。
- 使用现有 Rust、SQLite 和工具执行框架，不引入 LangGraph 依赖或通用图调度 DSL。
- 使用分类验收：代码和文件任务采用自动检查与产物证据；分析任务保存结论和来源，并明确标注模型自检。
- 对话可见工具文本累计估算达到 24,000 tokens 时预警，达到 32,000 tokens 时建议保存交接并新开对话；阈值可配置。
- 现有后台 ACP Goal 的行为、权限和历史数据保持兼容。

## 2. 用户流程与阶段约束

### 2.1 对话命令

| 用户输入 | 工具行为 |
| --- | --- |
| 开启目标模式：<目标> | 调用 goal_mode_start，创建规划中的目标，设为当前目标 |
| 继续本地当前任务 | 调用 goal_bootstrap，读取当前目标及恢复包，再根据阶段继续 |
| 查看当前目标进度 | 读取目标、节点、问题、验收证据和预警状态，不启动执行 |
| 我已看过此版本计划，现在开始执行 | 调用 goal_confirm_plan，绑定保存版本与哈希；成功后再认领节点 |
| 修改当前目标计划：<变化> | 进入重新规划流程，保存新版本、重新等待用户确认后再继续受影响节点 |
| 暂停当前目标 | 保存检查点并暂停新业务派发；已派发操作保留并核对 |
| 退出目标模式 | 保存检查点、暂停目标并解除当前窗口的模式绑定；保留当前目标指针和已有操作记录 |

以上是由模型识别并调用工具的自然语言约定，不声称给 ChatGPT 网页安装了原生斜杠命令解析器。工具说明和内置工作流指引必须给出这些入口。

### 2.2 主流程

网页开启目标模式 → 读取项目与讨论需求 → 形成并展示计划 → 网页模型通过工具保存本地计划 → 校验计划及落盘结果 → 等待用户阅读并在对话中明确通知开始 → 确认具体版本与哈希 → 认领节点 → 执行并存证 → 验收 → 下一节点或返工 → 总体验收 → 完成。

| 阶段 | 允许的行为 | 转移条件 |
| --- | --- | --- |
| planning | 讨论、读取源码/资料、检查现状、保存需求和计划草稿 | 完整计划通过结构检查且物化成功 |
| awaiting_confirmation | 查看计划、继续只读调查；实施等待用户在对话中明确通知开始 | goal_confirm_plan 确认当前版本与哈希 |
| ready | 读取计划和恢复包，认领首个或待恢复节点 | 当前版本已经用户确认，计划文件有效，未决操作已核对 |
| executing | 在当前节点及授权范围内执行，更新状态并记录证据 | 节点提交验收或出现阻塞/暂停 |
| verifying | 按计划执行节点验收和最终验收 | 通过后推进；失败则保存问题并返工 |
| paused / blocked | 读取、补充问题、核对原操作，保存交接 | 暂停解除或阻塞得到处理，再显式接手 |
| completed / cancelled | 查看历史和结果；不自动启动另一个目标 | 返工须显式创建新尝试并重新验证 |

规划之前应先读取真实项目材料。planning 和 awaiting_confirmation 均允许 read/search 工具、present_document 文档解析/表格/预览/分页/读取 Job 续取，以及 document_restore 不带 backup_id 和 job_id 的备份目录查看；无需已保存或确认的计划、节点认领或 goal_context。所有文档工具的 project + job_id 续取也属于结果观察，不会发起新操作。解析工作进程的执行权限与 Goal 的实施确认分开判断，项目、权限、Session 和 Job 校验照常执行。

planning 阶段不允许通过绑定 Goal 的工具修改业务文件、启动实现命令、安装依赖或部署。保存计划使用专用、路径固定的操作。通用 run_shell/run_process 不能因调用方声称“只读”就绕过规划阶段限制。

规划讨论期间，goal_checkpoint 可以保存已澄清的需求、约束、决策、必要问题和 plan_draft；允许草稿尚不完整，但不能因此进入 ready。完整计划的结构检查和物化只通过 goal_plan_save 完成。退出模式不隐式取消已派发 Job，恢复前仍需核对其实际结果。

计划保存成功一律停在 awaiting_confirmation。即使最初要求完成整个任务，也不能代替用户阅读本地计划后的明确开始指令。确认信息由网页模型忠实转达，保存具体版本、哈希及文本；协议不将该文本冒充独立认证的人类签名。计划存在本身不扩大项目或执行权限。

## 3. 本地计划及状态的权威来源

### 3.1 存储位置

以本机 WebCodex Server 为状态权威，使用其配置的持久数据目录：

```text
<WEBCODEX_DATA>/
  webcodex.db
  goals/<goal_id>/plans/v<plan_version>/
    plan.json
    plan.md
```

SQLite 是计划版本、任务状态、当前目标、检查点、操作记录和计量记录的唯一权威来源。plan.json 是结构化计划的可检查物化副本；plan.md 从同一版本确定性生成，供用户阅读。进度不通过反复改写这两个计划文件维护。

计划文件路径只能由服务端生成的 goal_id 和版本号构造，限定在上述目录内；拒绝路径逃逸和可替换路径别名。状态目录使用持久绝对路径，不依赖临时目录或浏览器本地缓存。

### 3.2 计划必须包含的内容

| 计划部分 | 必填内容 |
| --- | --- |
| 需求基线 | 用户目标、范围、约束、已有成果、关键假设、尚未解决的必要问题 |
| 最终交付 | 需要交付的结果或产物，以及“做到什么才算完成”的明确说明 |
| 最终验收 | 稳定 criterion_id、通过条件、验收方法、所需证据、验证来源类别 |
| 命令验收输入 | 顶层 verification_paths 用于最终命令验收和节点默认值；节点非空 verification_paths 覆盖默认值，避免依赖未来产物。命令验收的有效清单不可为空，全计划合并最多 64 项；当前检查所需路径指纹不可读时不能执行或复用通过证据 |
| 节点步骤 | 稳定 node_id、顺序、目的、输入引用、执行内容、输出、关联验收项 |
| 节点验收 | 本节点如何判断完成，失败后回到哪里，什么情况必须阻塞 |
| State 管理 | 要保存的事实/决策/问题/产物引用，允许更新的字段，检查点时机和恢复动作 |
| 完成路径 | 各节点怎样覆盖最终验收条件，最终验收在哪里执行 |

验收方法至少支持文件存在/内容检查、结构化命令与退出状态、产物指纹、已有运行证据、带来源的模型自检。模型自检不能伪装成独立审稿或机器验证。

每一项必需的最终验收条件必须映射到节点或最终验收阶段。计划不能把“代码已经写完”“模型说已完成”作为唯一的代码任务验收依据。

State 使用固定领域字段加有界任务事实，不允许计划上传任意执行代码或自定义状态机程序。计划声明字段更新与证据要求，服务端状态转移仍由受控实现决定。

### 3.3 计划保存与执行门槛

数据库事务不能和文件写入假装为同一原子事务，采用可核对的两阶段保存：

1. 校验计划结构、必要问题、节点顺序及验收覆盖，幂等保存不可变计划版本，记录待物化状态；此时不开放执行。
2. 在受控目录使用临时文件和原子发布写入 plan.json、plan.md；读取并核对文件哈希与预期内容。
3. 保存两个文件的物化回执、计划哈希及当前版本，校验目标 preparation_revision 后将阶段改为 awaiting_confirmation。
4. 中断或响应丢失时，按同一版本及幂等键检查已有文件并完成原保存，不重复创建版本，也不覆盖不匹配文件。

计划保存幂等键与规范化请求指纹绑定：同键同内容恢复原版本和结果，同键不同内容返回冲突。重复请求不能重新发布一个不同计划。

认领节点和派发绑定 Goal 的业务操作都检查当前计划版本、物化状态以及匹配版本和哈希的用户确认。计划文件缺失、被修改或版本不一致时，暂停新的业务派发，提示显式保存正确的新版本并重新确认；不得静默把编辑后的 Markdown 当成新计划。

重新规划创建新版本，保留旧版本并清除原执行确认。执行步骤的 plan_version 与最终验收合同的 acceptance_contract_version 分开记录：普通步骤调整不能删除必需验收项，也不能把失败的自动检查降为模型自检。用户明确改变目标时，通过 change_request 保存忠实转达的请求，建立新的验收合同版本并保存 acceptance_changes；请求文字本身不作为独立人类身份认证。新版本物化后仍须重新确认。已开始任务的旧执行必须先停止新派发并核对未决操作，受影响节点及后续串行节点需要复核。

## 4. 运行状态与可靠执行

### 4.1 数据对象

| 对象 | 核心字段或责任 |
| --- | --- |
| HostGoalRecord | 目标身份、所有者、固定项目身份/根目录、阶段、revision、当前计划版本、验收合同版本、当前节点 |
| GoalState | 已完成摘要、任务事实、结论与来源、决策、未解决问题、产物/证据引用、下一步 |
| Node | 稳定 ID、规格版本、工作说明、输入输出、验收方式和状态 |
| NodeAttempt | 节点尝试 ID、执行代次、状态、关联操作与 Job、结束或中断原因 |
| Checkpoint | 目标和计划版本、状态更新、证据引用、操作水位、下一步及交接信息 |
| CurrentGoalRef | 所有者明确选中的项目身份、根目录身份和目标 ID |
| ContextMeter | 当前对话计量身份、估算累计量、计量来源、已提示级别及未计量内容标记 |

一个节点可以跨多个对话，一个对话也可以完成多个节点。节点切换与对话计量切换相互独立。

### 4.2 执行规则

- 节点开始、阶段结果、重要决策、阻塞、验收和交接时保存检查点；工具操作结果另有持久记录。
- 状态更新、检查点和幂等结果在同一事务提交，用 expected_revision 拒绝旧状态覆盖。
- 对绑定 Goal 的操作，显式携带 goal_id、node_id、attempt_id、plan_version 和 operation_id，并在真实执行入口校验。
- 操作派发前保存意图，operation_id 绑定规范化操作参数指纹；同 ID 同内容恢复原记录，不同内容返回冲突。响应丢失或服务重启后核对原操作、Job、已登记原生 Run 和产物，未知结果不能被当成未执行。
- 原生 coding_agent_start 的回执可绑定并恢复同一 Run；只有已知原生入口创建可信标记，任意插件的 run_id 不进入该观察路径。Run 未结束或结果未知时不替换执行；Run 结束不等于 Goal 已通过验收。
- 新对话接手会阻止旧 Attempt 的新派发。存在未决操作时，先核对，确认后再开放新业务写入。
- 旧 Attempt 的迟到结果只能补充原操作记录，不能推进新 Attempt 或更改当前计划。
- 验收结果绑定验收合同版本、计划/节点规格版本、Attempt 和检查时的产物指纹。检查进行中改变相关输入会使本次证据失效；后续节点可以合法修改前序中间产物，历史节点保留当时的阶段证明。最终验收重新检查当前交付，不冻结全部历史产物。
- 当前节点验收通过才能进入下一节点；全部必需节点和最终验收通过才能完成目标。
- checkpoint 的 state 是字段级补丁：省略字段保留，facts 按键合并、null 删除该键，显式数组替换、plan_draft:null 清空。历史检查点不因此丢失，不能用部分摘要覆盖完整问题数组。

规划阶段的门槛必须覆盖直接工具调用、通用网关和专用执行入口，而不只在 goal_claim_node 中检查。实现一个共享 Goal admission checker；静态工具在现有权限门附近调用，插件/SSH 等动态工具在实际 effect 解析完成后的专用治理入口调用。仅在普通 dispatch 路径加检查会遗漏提前转发的动态工具。

明确开启模式的对话，若宿主提供可靠 ClientWindow，可保存精确主体/窗口/项目根身份绑定，只用于收紧准入。无可靠窗口身份时，返回 explicit_context_only：同一显式 context_epoch 可建立调用方携带的弱绑定，使携带它但遗漏执行绑定的业务变更同样受控；省略或更换该标识的调用无法归属于原对话。显式 goal_context 始终校验其目标。绑定不授予权限、不生成 Workflow Session，也不证明模型记得上下文。

普通未启用目标模式的工作流保持原语义。外部编辑和不属于目标模式的独立操作通过产物指纹检测变化，不承诺全局文件互斥或所有外部效果恰好执行一次。

## 5. 上下文预警与换对话

### 5.1 计量边界

网页端当前没有可用的完整上下文 used_tokens/context_window_tokens。ACP Provider 的 usage_update 属于另一条执行链路，不能用于网页预警。

第一版统计 WebCodex 可见工具文本的参考 token 累计，使用本地 o200k_base 参考编码并保存算法版本。计入有效工具参数、最终结构化结果、独有文本内容、错误和恢复包，避免同一结果的两种表示被重复统计。

用户普通聊天、模型普通回答、其他应用、系统提示和宿主压缩不可见；图片二进制和引用文件大小不折算为文本 tokens，标记未计量模态。这不是实际上下文占用率，也不能由低计数推断一定尚有足够余量。

### 5.2 阈值及归属

| 默认阈值 | 行为 |
| --- | --- |
| 小于 24,000 | 展示可见文本累计估算及部分观测标记 |
| 达到 24,000 | 提醒整理并保存阶段进度 |
| 达到 32,000 | 建议保存交接后新开对话 |

阈值可配置，要求预警阈值小于换对话建议阈值。提示在工具交互和目标面板中呈现；纯聊天没有工具交互时不承诺实时预警。

计量按对话独立持久化。同一对话切换目标、完成节点、重读恢复包都不清零。优先复用可靠宿主对话标识的哈希；缺失时使用显式 context_epoch，不能归属时显示不可用，不汇总到公共桶。传输会话 ID 不直接等同聊天 ID。

同一计量事件去重，真实的新读取、重读或轮询继续累计。能识别的传输重放不重复入账；没有稳定调用标识时保守累计并标注误差来源，不能借业务 operation_id 去重所有真实交互。

首次跨阈值完整提示，后续只保留简短状态。预警不自动取消 Job 或终止节点。只有检查点提交成功，才显示“任务已保存，可以换对话”；保存失败必须报告失败。

### 5.3 交接与恢复

用户新开对话后输入“继续本地当前任务”，goal_bootstrap 读取本地 CurrentGoalRef，重新检查项目/目标权限，返回当前阶段、计划版本、完成摘要、当前节点、阻塞项、未决操作、下一步和证据入口。

默认摘要及详细数据片段不超过 8 KiB；goal_read(view=node) 的完整节点包不超过 16 KiB，只有该视图登记认领所需的读取回执。摘要明确标记 partial。view=detail 按 goal、plan、state、checkpoints、attempts、operations 分段并用 next_cursor 返回 JSON 文本片段；完整拼接后才能解析。初始需求可在尚无计划时通过 goal 段读取。各响应计入当前对话的累计量。

planning 阶段中断的新对话继续规划；awaiting_confirmation 阶段继续等待用户阅读并明确确认；ready 阶段读取计划后认领节点；executing 阶段先核对未决操作；completed 只显示结果，不自动切换目标。缺少有效当前指针时提示列出并明确选择目标，不猜测“最近目标就是当前任务”。

更换对话只新建相应计量上下文，不清空计划、节点、检查点或问题。旧对话只返回简短保存回执和续接指令，完整恢复包留给新对话读取。

## 6. 接口及与现有架构的集成

| 接口 | 责任 |
| --- | --- |
| goal_mode_start | 创建 planning 目标，保存初始需求与当前目标选择，建立可用的显式模式绑定 |
| goal_plan_save | 校验并保存完整计划版本，物化本地文件；完成回执后置为 awaiting_confirmation |
| goal_confirm_plan | 保存用户在网页对话明确通知开始的原意，绑定当前版本与哈希，成功后置为 ready |
| goal_bootstrap | 恢复当前或指定目标；按明确继续意图启用当前对话模式，返回状态与计量身份，不自动开始节点 |
| goal_list / goal_read | 统一读取 ACP/Host 目标、当前计划、节点与分页历史 |
| goal_claim_node | 校验计划已就绪和执行前置条件，开始、接手或返工节点 |
| goal_checkpoint | planning 时保存草稿需求/约束/问题/计划；执行时保存进度与证据；支持暂停、退出模式和交接回执，不能绕过计划就绪或验收条件 |
| goal_check_node | 按当前不可变计划执行验收，保存证据，决定推进或完成 |

不新增与 goal_mode_start 重叠的 goal_create。已有 goal_start/goal_resume 保持 ACP 语义，拒绝把 Host 目标送入 ACP worker。

实现采用独立的 wc_host_goals 及 Host 计划、Attempt、检查点、操作、请求回执、当前目标和计量表。原 wc_goals 不增设共享 driver 列，旧 ACP 快照和后台扫描保持原行为；公共 goal_list / goal_read 聚合两类记录并投影 driver。这个内部存储调整不改变统一发现和读取的用户行为。Host 不使用 ACP worker_epoch 和绝对总截止时间。

统一读取入口按实际 driver、所有者和当前项目权限复核，过滤未授权记录。Host 进度和计划保存不强制要求 coding_agent 权限；文件、命令、Job 等实际效果仍检查其原权限。

同步 ToolCall、工具注册、输入输出 Schema、OAuth 策略、MCP、OpenAPI、通用/专用执行入口、审计和前端投影。模式绑定只能收紧准入，不能绕过原有权限或依靠 recording_session_id 假装执行隔离。

复用 Workflow Session 的交接摘要、验证和 Job 查询作为证据来源；长期业务状态保存在 Goal。Memory 只承担跨任务知识，不复制为第二份任务进度。计划和状态副本不要求用户手工编辑数据库。

目标面板展示阶段、计划路径及版本、节点、阻塞项、下一步、检查点、验收来源和预警状态。采用步骤列表，不新增图形流程编辑器。

## 7. 实施步骤及最终验收

### 7.1 实施节点

1. 类型与存储：Host Goal、计划版本、节点、Attempt、Checkpoint、当前目标和计量表；迁移保护旧 ACP。
2. 规划入口与计划物化：模式启动、计划结构检查、JSON/Markdown 生成、物化核对、awaiting_confirmation 和版本确认门槛。
3. 节点执行与阶段准入：绑定元数据、版本与执行代次校验、操作意图/回执、验收与返工。
4. 新对话恢复：当前目标发现、按阶段恢复、8 KiB 恢复包、补读与未决操作核对。
5. 预警与面板：对话计量、24k/32k 提醒、交接回执、模式与节点可视状态。
6. 契约与验收：按变更范围执行存储、运行时、工具契约和前端专项测试，完成无聊天历史客户端的续接实验。

### 7.2 必须通过的最终验收条件

| ID | 目标 | 验收方式 |
| --- | --- | --- |
| A01 | 开启模式首先规划，不直接执行 | planning 中绑定 Goal 的业务变更被拒绝；专用计划保存及只读观察可用 |
| A02 | 计划包含完整验收与状态管理 | 缺最终验收、验收方法、节点覆盖或 state 更新规则的计划不能 ready |
| A03 | 本地计划成功保存才能执行 | 文件缺失、哈希不符、只完成一份文件、DB 回执未提交时不能派发业务操作 |
| A04 | 保存中断可以恢复而不重复建版本 | 在 DB/文件/回执边界注入失败，重复原请求核对同一版本并恢复 |
| A05 | 新对话可直接拿到本地当前任务 | 无旧聊天历史的新客户端 bootstrap 正确返回目标、阶段、节点、问题和下一步 |
| A06 | 规划阶段也能跨对话续接 | 讨论中断后保留需求、约束、必要问题和草稿，不误进入执行 |
| A07 | 跨天和重启保留任务状态 | 重开 SQLite/重启服务后目标、计划、指针、检查点及未决操作一致 |
| A08 | 接手与重试不会错误重做 | 两个对话竞争接手、旧代次提交、响应丢失、未知 Job 的故障注入测试 |
| A09 | 验收覆盖真实交付并随变化失效 | 失败检查阻止完成；返工、计划变更和产物变化使相关旧结论失效 |
| A10 | 预警归属正确且不会假报容量 | 24k/32k 边界、配置、重复 bootstrap、同对话换目标、新对话计数、模态/重放测试 |
| A11 | 保存失败不宣称可安全交接 | 检查点写入失败时无“已保存”提示，恢复展示最后成功水位及后续操作 |
| A12 | 权限和旧行为兼容 | 未授权目标/计划不可读；缺少实际执行权限不能执行；旧 ACP 数据及循环回归通过 |
| A13 | 规划阶段不能经动态工具或遗漏绑定绕过 | 插件/SSH 实际变更被共同阶段门拦截；可靠绑定窗口缺少或伪配目标信息的变更被拒绝；无窗口边界和普通模式兼容 |
| A14 | 重新规划不能降低最终验收制造完成 | 调整步骤不改变验收合同；新合同留存差异与原因，并使受影响旧证据失效 |
| A15 | 保存计划不能代替用户开始确认 | 计划已物化但未确认时不得认领或派发；旧版本、旧哈希和重新规划前的确认均不能授权当前版本 |

仅修改设计文档时不运行编译。本方案实施后按受影响层运行最小充分测试；跨层准入和真实恢复链路使用有针对性的集成实验，不以模型自述代替通过证据。

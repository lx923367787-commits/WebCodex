# ChatGPT 网页目标模式：先保存计划，确认后执行

本文是当前操作说明，已于 2026-09-29 对照源码校准。历史设计、验收和部署记录不能替代本文或当前工具契约；实际调用仍以工具返回的阶段、绑定与证据为准。

本模式由 ChatGPT 网页对话调用 WebCodex 工具推进。目标、计划、节点、问题和验收证据保存在本机 Server；更换对话后可以读取同一个任务。

完整流程是：**开启目标模式 → 读取项目资料、讨论需求 → 网页模型生成并保存本地计划 → 用户阅读 → 用户在网页对话明确通知开始 → 读取当前节点上下文 → 认领并执行节点 → 验收。** 保存计划本身不授权执行，也不会启动后台 ACP 任务。

本文说明源码接口和操作约定，不表示当前安装已更新。源码测试和构建证据见 [验收记录](HOST_GOAL_MODE_ACCEPTANCE.zh-CN.md)；旧的后台 Provider 模式见 [ACP 目标模式](GOAL_MODE.zh-CN.md)。

## 1. 连接与启动

先让 ChatGPT 网页使用的 WebCodex 插件／工具连接到包含这些接口的本机 Server，并选择已授权的项目。工具列表应能找到 `goal_mode_start`、`goal_plan_save`、`goal_confirm_plan` 和 `goal_bootstrap`。如果连接的是旧版 Server，仅修改源码或另开对话不会使新接口生效。

普通编码启动摘要只保留目标模式的启动与恢复入口。`category=goal` 的发现结果只是工具目录；首次使用某个 Goal 工具前，按确切名称调用 `tool_manifest(tool_name="...")` 读取完整契约，不能凭名称或一句简介猜参数。已经掌握且未变化的契约可以复用。

`goal_mode_start` 和 `goal_bootstrap` 成功后会直接返回共享的 `workflow_overview`，说明新任务、恢复任务及关键边界。它只是流程地图，不要求从头重跑，不授予权限，也不代替 `goal.phase`、确认记录、`continuation`、节点读取回执、执行绑定和验收结果。

网页模式不要求配置 ACP Provider。读取和保存目标需要相应项目权限；执行命令、启动 Job、修改文件或调用插件仍检查原有权限。

在 ChatGPT 对话中输入：

```text
开启目标模式：为这个项目实现……，最终需要……，请先与我讨论需求并保存计划。
```

这是模型识别后调用工具的自然语言约定，不是给 ChatGPT 安装的原生斜杠命令。模型调用 `goal_mode_start` 后目标进入 `planning`，此时可以读取资料、澄清需求和保存草稿。应先读取实际项目材料，再据此形成计划。`planning` 和 `awaiting_confirmation` 均允许读取、搜索、`present_document` 文档解析（含表格、分页、预览及读取 Job 续取），以及 `document_restore` 不带 `backup_id` / `job_id` 的备份目录查看；这些调查操作不要求先保存或确认计划，也不要求认领节点或携带 `goal_context`。所有文档工具只携带 `project + job_id` 续取已有任务时也属于结果观察，不会发起新操作。解析工具内部启动受管工作进程，不等于开始实施。修改文件、编辑或转换文档、恢复备份、通用命令执行等实施操作仍须通过计划确认；原有项目、权限与 Job 校验继续生效。

常用对话命令：

| 用户输入 | 模型应执行的操作 |
| --- | --- |
| 开启目标模式：…… | 创建规划中的目标，设为本地当前目标 |
| 把讨论结果整理成计划并保存到本地 | 调用 `goal_plan_save`，返回计划路径、版本和哈希，等待确认 |
| 我已看过这个版本的计划，现在开始执行 | 调用 `goal_confirm_plan`，用 `goal_read(view="node")` 读取首个节点，再认领执行 |
| 查看当前目标进度 | 读取目标、节点、问题、检查点和验收记录 |
| 保存进度，我要换一个对话 | 保存 `handoff` 检查点；只有提交成功才能说明已保存 |
| 继续本地当前任务 | 调用 `goal_bootstrap`，读取本地恢复信息后按当前阶段继续 |
| 修改当前目标计划：…… | 保存新版本；本地生成后重新等待用户确认 |
| 暂停当前目标 | 保存进度并暂停新业务派发；核对已有操作 |
| 退出目标模式 | 保存进度、暂停目标、解除当前窗口绑定；不删除任务 |

## 2. 本地计划与用户确认

计划由 **ChatGPT 网页中的模型通过 Server 工具生成**。不是要求用户复制本次 Codex 研发对话，也不是让用户手工维护数据库。

在网页聊天里告诉 LLM 任务文件夹，例如：“在 `E:\work\测试任务` 中执行本次任务”。LLM 先选择包含该文件夹的已注册项目，再调用 `goal_mode_start(task_directory="E:/work/测试任务")`；也可传项目内相对路径。未传时使用所选项目根目录。项目外目录需要先选择或注册为项目，不能借此绕过项目权限。

新目标的文件由对应 Runner 保存到选定任务目录：

```text
<用户选定的任务文件夹>/
  goals/<goal_id>/plans/v<plan_version>/
    plan.json
    plan.md
  handoff/<goal_id>/checkpoint-<sequence>/
    handoff.json
    handoff.md
```

回包的 `task_files` 显示任务目录、目标目录和交接目录的实际绝对路径；`plan_artifacts`、`handoff_artifacts` 给出具体文件。任务目录固定保存在目标记录中，换对话、重启及同请求重试不会改目录。执行工具的 `cwd` 应使用该任务文件夹；项目相对文件参数和验收路径仍相对于已注册项目，子任务目录须带前缀。

`plan.json` 与 `plan.md` 来自同一不可变版本，确认、认领和验收前读取 Runner 上的真实文件指纹。交接 JSON/Markdown 只记录确切的已提交 checkpoint；后续状态写新序号文件，不覆盖旧交接。文件写入或回包中断后，重试同一请求/幂等键会核对并补齐文件。若交接回包显示 `checkpoint_saved=true` 但文件导出失败，交接和旧上下文退休已经提交，不能重新执行业务；按原请求重试文件发布。

SQLite 继续保存运行时的身份、权限、计划版本、审核及恢复状态。历史目标未记录 `task_directory` 时仍从原 Server 数据目录读取，不移动旧文件，也不修改已确认计划哈希；新建目标才使用上述任务目录布局。

每份计划必须说明：

- 最终目标、约束和交付结果。
- 最终验收条件、验收方式及需要的证据。
- 串行节点的输入、工作内容、输出、节点验收和失败处理。
- 节点与最终验收条件的对应关系。
- State 中事实、决策、问题和产物引用的保存规则、检查点时机、恢复步骤。

包含命令验收时，必须用 `verification_paths` 明确列出会影响检查的项目内输入文件和产物，不能只列一条命令。顶层路径用于最终验收并作为节点默认值；节点可以用自己的 `verification_paths` 覆盖默认值，避免早期步骤依赖尚未生成的最终产物。路径必须指向具体文件，且全计划合并不超过 64 项。当前检查声明的验收文件指纹无法读取时，命令不能被视为可靠通过，也不能复用此前成功的 Job。修改这些路径清单属于新计划，必须重新保存并确认。

为了让新对话完整读到当前步骤，共享需求和单个节点各不超过 8 KiB，二者合计不超过 12 KiB；完整计划仍可以包含多个节点，最多 128 KiB。超限时应拆分节点或引用本地说明材料，不能截断必要的验收条件。

保存分为数据库登记版本、发布两份文件、核对文件内容并登记回执。任一步未完成，都不能认领执行节点。发布成功后的阶段是 **`awaiting_confirmation`**。

用户阅读该版本后，需要在 ChatGPT 对话中明确通知开始。模型调用 `goal_confirm_plan`，提交当前 `plan_version`、`plan_sha256` 和用户的确认原意；成功后才进入 `ready`。确认绑定特定版本和哈希，旧版本确认不能启动新计划。

确认文本由模型转达，协议不把它当作独立认证的人类签名。模型不得自己编写批准、把保存成功当成批准，或用最初“完成这个任务”的要求替代用户看完计划后的开始指令。

修改计划会保留旧版本、清除执行确认并使节点需要重新验收。普通步骤调整不能悄悄删除或降低最终验收条件。用户明确要求修改目标或验收合同时，模型通过 `change_request` 忠实保存请求；新版本记录变更摘要并递增验收合同版本，仍需用户阅读后重新确认。

如果计划文件缺失、被手工修改或哈希不符，业务执行会被阻止。不要把编辑后的 Markdown 当成已批准计划；通过工具保存正确的新版本，再确认执行。

## 3. State、节点与验收

本地 State 保存完成摘要、事实、决策、未解决问题、产物引用、下一步以及可选的规划草稿。节点执行身份、状态版本、检查点、工具操作与 Job 记录分别持久化。一个节点可以跨多个对话完成。

`goal_checkpoint.patch.state` 是部分更新：未提供的字段保留；`facts` 按键合并，某个键的值为 `null` 时只删除该键；明确提供的数组整体替换；`plan_draft: null` 清空草稿。存储中的事实值仍是字符串，历史检查点保留原记录。需要修改完整的问题或决策数组时，先读取完整 State，不能把紧凑摘要中的部分条目当成完整数组覆盖。

| 阶段 | 含义 |
| --- | --- |
| `planning` | 读取材料、讨论需求并形成计划，实施未开放 |
| `awaiting_confirmation` | 两份本地计划已核对，可继续只读调查，实施等待用户通知开始 |
| `ready` | 当前版本已确认，可以认领下一个节点 |
| `executing` / `verifying` | 执行或验收当前节点；验收实现保留检查操作和证据 |
| `paused` / `blocked` | 暂停或受阻，先读取问题、核对已有操作 |
| `completed` | 必需节点及最终验收已通过 |
| `cancelled` | 已取消，不会自动继续或切到其他目标 |

认领前，在当前对话调用 `goal_read(view="node", node_id=...)`。只有完整节点包返回的 `context_read.complete` 会登记本次读取；普通摘要或 `goal_bootstrap` 不满足这道门槛。`goal_claim_node` 返回当前节点和 Attempt 的执行绑定。业务工具以及执行期间的检查点调用携带该 `goal_context`，再为每个操作增加稳定的 `operation_id`。旧 Attempt、旧计划版本、错误项目或过期状态不能覆盖当前任务。

阶段结果、重要决策、失败、暂停和交接都应调用 `goal_checkpoint`。检查点只能保存允许的进度字段，不能通过填写“已完成”直接跳过验收。节点验收通过后才能推进；返工会使该节点及后续步骤重新检查。

验收区分证据来源：

- 文件存在、内容和命令检查由运行时执行；模型不能提交伪造的 `automated` 通过结果。
- `review` 条件接受带来源的 `model_self_check`，明确属于模型自检，不冒充机器验证或独立审稿。
- 命令验收使用持久 Job，保存所用输入指纹；旧成功 Job 不能被重新绑定到已改变的产物。
- 当前节点的检查前后核对自己的输入和产物；最后一个节点还会重新执行最终验收。历史节点证明当时完成的阶段成果，后续步骤可以按计划继续修改同一个文件，不要求中间产物永远保持原字节。主动返工旧节点仍会使该节点及后续步骤重新执行。

验收记录证明检查当时的结果，不表示后台一直监视所有外部文件变动。

### 失败后的有界修复

已确认计划中的当前节点是受影响业务的边界。已知业务操作失败、节点机器验收失败或模型审核拒绝，会持久保存 `recovery`。`business_suspended=true` 时，普通实施调用被拒绝；读取、诊断、原 Job/Run 的观察及符合现有权限的修复仍可进行。下一节点必须等原节点及适用的最终验收通过。

宿主模型收到失败后应主动继续以下流程，不需为已批准范围内的修复再次询问用户：

1. 读取 `recovery.failure`，必要时通过 `goal_read(view="detail", section="repair")` 查看完整失败和诊断记录。当前 Attempt 已结束时，先读取并重新认领同一节点。
2. 在修复操作的 `goal_context` 中加入 `repair: {"repair_id":"<回包中的当前 ID>","diagnosis":"观察到的原因及拟做的针对性修复"}`。每轮首次调用必须保存具体诊断；修复身份只收紧准入，不扩大项目或工具权限。
3. 修正后调用 `goal_check_node`，继续携带修复身份。沿用原计划的文件、命令、输入指纹和审核要求；工具执行成功、模型声称已修复、保存检查点均不能解除门槛。
4. 验证失败时读取新的修复 ID，重新诊断并继续；原验收通过后 `business_suspended=false`，按原计划认领下一节点，后续调用移除修复元数据。

每次修复事件最多 3 轮、32 次实施操作、30 分钟，以最先达到者为准；审核还有原计划自己的轮数上限。预算写入数据库，暂停、重启、换对话、重新认领均不重置；未解决的修复也不能通过换计划清除。预算耗尽后保存证据并说明所需人工决定，不无限重复。

结果未知不属于已知失败：先核对原 Operation/Job/Run，不能盲目启动替代执行。修复期间仍遵守取消、权限、上下文退休及原执行身份约束。修复 ID 声明本次调用用于修复，运行时校验其节点和预算；它不能从任意 shell 内容中证明每条命令的业务含义。宿主模型负责具体诊断及修复决策；本机制不自动唤醒已结束的网页对话。

## 4. 换对话与上下文预警

新 epoch 的默认计量阈值（已有 epoch 保持原策略）：

| 可见工具文本累计估算 | 提示 |
| --- | --- |
| 少于 600,000 tokens | 显示累计估算 |
| 达到 600,000 tokens | 提醒整理并保存阶段进度 |
| 达到 800,000 tokens | 持久进入 DRAINING，拒绝新业务和新认领，只允许当前 Goal 收尾 |

新 epoch 初次启动时可以通过 `context_warning_tokens` 和 `context_handoff_tokens` 配置阈值，后者必须更大。已有 epoch 不通过重复启动改写策略，DRAINING/RETIRED 状态也不会因重启或阈值变化退回。这是本地参考编码对 **WebCodex 可见工具文本** 的累计估算，不是 ChatGPT 的真实容量或占用率。普通聊天、系统提示、其他工具、图片内容和宿主压缩不可完整观测。纯聊天期间没有工具交互时，不会保证实时提醒。

交接调用 `goal_checkpoint`，把 `"action":"handoff"` 放在 `patch` 中。相同请求/key 重放同一 Checkpoint；源对话进入等待接管，停止新业务，但此时没有退休。原 Goal、已确认计划、最后进度及成果保留。

现有本地调度器发现等待记录后，通过受信控制接口分配尝试（native 使用 `handoff_begin_attempt`；原 host-window 内部接口保留 `goal_handoff(action="begin_attempt")`）。Server 持久分配唯一 attempt_id 和截止时间，再实际调用原网页启动适配器。保留既有 120 秒启动延迟；接管等待从 Server 分配尝试起单独计时，默认 300 秒，用 `WEBCODEX_HANDOFF_TAKEOVER_TIMEOUT_SECS` 配置（1–3600 秒）。它不修改 CLI 超时或 600K/800K 阈值。最多首次加三次重试，共四次；重复发现、回调、服务重启不清零预算。同一次尝试不重复发送。换尝试前先撤销旧候选资格，结果丢失先查询 Server 的实际状态。

候选对话使用自己的可信 host window，不接受源 epoch 或自报身份。`goal_handoff(action="prepare")` 核对 project、Goal、Checkpoint、计划版本与交接包，实际读取文件指纹（native 经 private broker，原路径经 Runner）；只返回本任务包和摘要。候选读取包后以精确 `package_sha256` 调用 `commit`。Server 在同一事务核对当前候选、未过期尝试、准备证明和旧执行链终态，切换执行所有者、推进旧节点 fence、退休源对话。新对话还须以 `status` 确认 `execution_granted=true` 才能继续原任务。创建网页、提示词发送、accepted/pending、bootstrap 或模型口头声明都不是接管成功。

切换前通过现有 StopJob/原生 Run 取消与观测机制处理旧后台链；仍有活动请求、未知结果或无法证明全链终止时停止交接，不能同时放行两个执行者。四次失败或不安全旧执行链使 handoff=`failed`、Goal=`blocked`、源上下文=`stopped`；不再自动恢复或启动第五次。报告“交接失败，已停止执行，已保留可人工恢复的状态”，不标记任务完成。只有用户明确要求后才可人工恢复。

handoff 保持同一个逻辑 Agent 身份，仅更换 run/网页对话，不创建替代 Goal。按用户后续确认，自己的 Memory 和已有会议授权保留；业务写入受持久 `task_goal_id`、当前 run 和新节点 claim 约束，不能读取其他 Agent 的私域。native 私域文件通道可以接续本任务，CLI/插件因缺少已验证的 OS 隔离仍被拒绝。

native 接入使用既有 BootstrapOnly 管理接口控制有限重试，显式配置控制凭据而不复用 Desktop user token。可信 OAuth 宿主须显式登记源窗口。启动器随后领取仅限当前尝试的 256-bit 一次性准备授权，只在发给目标新聊天的局部消息中携带；本地 request、回执、文件名、日志和环境不保存原文，目标宿主聊天可能留存授权消息。服务端仅存哈希，首次 `prepare(launch_claim=...)` 同事务核验 OAuth principal、source/pending run、同 Goal/Checkpoint/attempt、原 deadline 和全新窗口，再授予 Pending 准备资格。不会因为凭证、网页创建或 prepared 就授业务权，仍必须实际读包核验再 commit/status。源窗口、其他 Agent、旧候选/撤销窗口不能兑付，同窗只可幂等读回原结果。

attempt UUID 与网页 URL 均不充当授权，不复制旧 run token 或改变全局 connector，也不需要猜测 URL 与匿名 `openai/session` 的对应关系。发行响应丢失先查状态，不能重发或旋转同次 grant；未成功就等待原截止时间，下一次尝试撤销旧资格。数据库排队时间计入期限，锁等待跨过 deadline 时拒绝准备或切权。真实网页接管仍未实测；自动化模拟不代表已验证外部网页端到端成功。接入限制及验证结果见 [本轮说明](HANDOFF_RELIABILITY.zh-CN.md)。

原 host-window 内部投影通过 `goal_list.latest_handoff` 和 `goal_read(view="handoff",source_context_epoch=...)` 发现交接；native 调度器使用管理接口 `handoff_list/status`，模型使用 `goal_handoff(status)`。`retired_at` 在实际提交前为 null，`created_at` 是交接准备时间；`resume_started` 仅在执行权提交时记录，不再以激活 bootstrap 作为自动交接成功依据。
## 5. 中断、重试与未知结果

请求超时不等于操作没有执行。保持原参数和幂等键，读取已有目标、操作或原 Job；不要随意换新键重新派发。

已知的验收命令可以根据不可变计划、保存的输入指纹和原幂等身份恢复原 Job。普通业务操作若结果仍未知，会阻止继续执行。运行中的 Job 必须观察其真实终态，不能由模型宣称已经停止。

若节点内明确调用原生 `coding_agent_start`，操作记录会保存该原生 Run 的身份和执行确定性。恢复时通过 `coding_agent_observe` 核对同一个 Run，必要时取消该精确 Run；等待权限、仍在运行或结果未知时不启动替代执行，也不能用人工报告覆盖。任意插件输出中的同名 `run_id` 不会被当成原生 Run。Run 结束只说明原执行结束，目标仍须经过节点及最终验收。

对于状态为 `unknown` 或崩溃后遗留 `intent`、且既无可观察 Job 也无已登记原生 Run 的业务效果，需要用户核对实际文件或其他外部结果。运行时仍在处理的活跃请求不能人工解除；只有请求已结束或丢失后，才能经用户明确核对恢复。模型通过 `goal_checkpoint.patch.operation_resolutions` 保存操作 ID、终态、核对说明、来源和用户确认原意。这属于 `operator_resolution` 人工核对；当前记录的来源字段为 `user_reconciliation_report`。核对记录与检查点、状态版本和幂等回执在同一事务提交，旧执行身份或无效状态不能先行改变操作结果。

内部 `check_*` 验收操作不能被人工标记为成功或失败。若尚无确定 Job 且输入指纹已经变化，系统不会重派原命令；用户明确核对后，只能取消这个不确定的检查，再认领新尝试针对当前输入重新验收。仍活跃的检查不能人工取消记录，已有 Job 必须观察或停止原 Job。

**人工核对只解决原操作结果的不确定性，不是机器验收证据，也不代替节点和最终验收。** 模型不能依据回忆编造确认；未知效果仍无法核实时，应保留阻塞状态。

## 6. 执行限制与旧模式兼容

可靠宿主窗口身份存在时，开启模式会为该窗口建立精确绑定，缺少或错误绑定的业务变更同样受到门槛限制。没有可靠窗口身份时返回 `explicit_context_only`：复用同一 `context_epoch` 的调用可以建立较弱的目标模式绑定，这些调用即使漏传 `goal_context`，也不能绕过规划或确认门。它是调用方携带的标识，不是经认证的网页身份；省略或更换该标识的未标记调用无法归属于原对话。显式携带 `goal_context` 的调用始终按其目标校验。任何绑定都不会新增项目或执行权限。

当前采用串行节点和用户主动新开对话，不自动操纵网页、不自动唤醒新对话，也不保证所有外部效果恰好执行一次。

一期可选只读控制器位于本机 `E:\wbecodex\chat-handoff\handoff_controller.py`，独立保存 STOP/暂停/阻塞和交接观测。使用它时显式传 `--db "<任务文件夹>/handoff/controller/<goal>/<source-epoch标识>/controller.sqlite3"`，其数据库和锁文件也跟随任务目录；每个源 epoch 使用独立数据库。不要把远端 Runner 路径猜成本机路径。用法及人工恢复步骤见该目录 README。`scripts/e2e_host_handoff.py` 只在隔离临时 Server/Runner 上验证显式 epoch 协议；其成功不代表真实网页无人交接或免风控。

内部使用独立的 `wc_host_goals`、计划版本、Attempt、检查点、操作、请求回执、当前目标与计量表。旧 ACP 目标继续使用原存储和后台执行循环；`goal_list`、`goal_read` 在公共接口上区分 `driver: host` 与 `driver: acp`。`goal_start`、`goal_resume` 仍属于 ACP 模式，不能把网页目标隐式交给 Provider 执行。
